# Orsy — implementation spec

**Orsy** is an orthographic syllabic chord layout for mesa3, derived from the Michela
machine-shorthand layout by way of the Midi4Text theory (analysed in `../midi4text/`).
The name is short for *orthographic-syllabic*; the parent theory's name refers to a MIDI
keyboard, which nothing here involves.

Everything below refers to the mesa3 mapping in `01-mapping.md` and
`02-caps-numbers-commands.md`, not to the original 20-key theory.

## Start here

This file began as the brief for the first implementation, which is now built: the
`bbq-orsy` crate and the mode in `bbq-keyboard/src/layout/orsy.rs`. It describes what was
built. To follow the code, read in this order:

1. **This file** — architecture, bit layout, algorithm, tests.
2. **`orsy-mapping.json`** — the frozen mapping. Every chord, with explicit key bits.
   Generated by `midi4text-analysis/freeze.py`, and regenerated only on purpose, after a
   deliberate chord change in the generators: they rank by corpus frequency, so a rerun
   for any other reason would silently move chords.
3. **`../../midi4text-analysis/m4t/theory.py`** — the reference implementation of the
   composition rules, ~150 lines. The Rust port must agree with it exactly.
4. **`01-mapping.md`** and **`02-caps-numbers-commands.md`** for the reasoning, only if a
   decision looks arbitrary.

`../midi4text/02-theory.md` explains the four Series and where the rules come from. It is
background; the executable truth is `theory.py`.

## Key bits and chord representation

Each hand uses the same bit numbering as the Dosh table, so the layout module can reuse
its scancode mapping. mesa3 has no upper pinky, so `0x010` is absent.

| key | bit | | key | bit |
|---|---|---|---|---|
| `a` pinky | `0x001` | | `n` middle top | `0x040` |
| `o` ring bottom | `0x002` | | `i` index top | `0x080` |
| `t` middle bottom | `0x004` | | `Sp` thumb | `0x100` |
| `e` index bottom | `0x008` | | `Bk` thumb | `0x200` |
| `s` ring top | `0x020` | | | |

    outer five (Series 1 / 4)   mask 0x067      a o s t n
    inner four (Series 2 / 3)   mask 0x388      e i Sp Bk

A chord is two `u16`s, one per hand. A Series is a mask, so splitting a stroke is four
`&` operations.

## Commands

Three sit on chords unassigned *within their own group*, so no syllable can produce
them. Shapes that are merely unattested in the corpus were rejected as not safe enough.

| command | hand | keys | bits | why it is free |
|---|---|---|---|---|
| `dosh_oneshot` | left | i + Sp + Bk | `0x380` | spare Series 2 chord; right hand carries the Dosh chord |
| `dosh_toggle` | left | e + i + Sp + Bk | `0x388` | spare Series 2 chord, and unmapped as 0x388 in Dosh, so one shape does both |
| `space` | right | Bk | `0x200` | spare Series 3 chord: the word-end marker with no vowel |

The other seven are **whole-stroke commands**: a Series 2 shape struck on the left with
nothing else on either hand. That is not unattested but useless. Series 2 alone spells its
consonant as a fragment leaning back onto the word before, and Series 4 writes every such
consonant in the stroke it ends, so no division of any word uses one: the writer never
chooses a lone consonant shape over the top 50,000 words of `count_1w`, and banning every
lone Series 2 shape, vowels included, costs no strokes and 0.001 keys per word. The shapes
keep their letters in any stroke with anything else in it; only the stroke that is
nothing but the shape is the command.

| command | keys | bits | letter it shadows | |
|---|---|---|---|---|
| `undo` | Sp | `0x100` | `r` | Backspace in Dosh |
| `capitalise_next` | e | `0x008` | `s` | |
| `join` | Bk | `0x200` | `l` | no space before the next word |
| `all_caps` | e + Bk | `0x208` | `m` | the next word in capitals |
| `capitalise_previous` | i + Bk | `0x280` | `t` | the word before, retyped |
| `uncap_next` | e + Sp | `0x108` | `e` | no capital on the next word, even after a full stop |
| `uncap_previous` | i + Sp | `0x180` | `u` | the capital taken off the word before |

The lone `i` and `e+i` (`o`) are left alone: they write a word's final vowel after a
closed syllable (`phot|o`, `tax|i`), which is the natural division there. The lone
`i+Sp` did the same for `u` in 102 of the top 50,000 words (`men|u`, `gur|u`); without
it they divide `me|nu` and `gu|ru` at the same stroke count, so it is `uncap_previous`.
The lone `w`, `c`, `p` and `n` are still free.

The commands that change the next word -- cap-next, all caps, uncap and join -- and undo
are recorded by the output stage as strokes that typed nothing, so undoing a mistaken one
takes back only the command. The two that act on the word before retype it in place. Undo was once all five
left outer keys, chosen to be hard to hit; that made the commonest correction the most
expensive stroke on the board, and that chord is free again.

**Punctuation that affects spacing is native**, which `02-caps-numbers-commands.md`
originally said it need not be. The chords extend the space command: `Bk` alone is a space,
and `Bk` plus one outer key is a mark. `Bk` is not a vowel form on its own, so no syllable
can reach any of them, and the family is two keys on the hand that already ends words.

Every mark attaches to what came before it, closed or not. They differ on the far side:
most owe the next word a space, while the apostrophe and the hyphen bind straight on to it,
so `don` `'` `t` is one word. The five commonest take the five one-key shapes, which is all
there are; the rest take two.

| stroke | mark | |
|---|---|---|
| `Bk` + `t` | `.` | owes a space, capitalises |
| `Bk` + `n` | `,` | owes a space |
| `Bk` + `s` | `'` | binds forward |
| `Bk` + `o` | `?` | owes a space, capitalises |
| `Bk` + `a` | `-` | binds forward |
| `Bk` + `o` + `t` | `!` | owes a space, capitalises |
| `Bk` + `s` + `n` | `:` | owes a space |
| `Bk` + `t` + `n` | `;` | owes a space |

They go through the output stage, so they are recorded, undoable, and visible to
retro-capitalisation. Everything else is still the Dosh escape, and 23 of the family's 31
shapes are still free.

Quotes and brackets are deliberately left out. They are asymmetric — the opener binds
forward and the closer back — so they need either two chords each or a notion of which one
is due, and getting that wrong is worse than reaching for the escape.

`dosh_oneshot` is held on the left while the right hand plays a literal Dosh chord — one
stroke, and every Dosh chord including the thumb layers is reachable. A mirrored form, so
the Dosh chord could be played left-handed, is **deliberately deferred**; it can be added
later without disturbing anything. The mesa3b's Fn keys do give a left-handed one-shot:
an Fn key struck with keys on the other hand only plays those keys through Dosh, and
tapped alone it is the toggle.

`dosh_toggle` is the left hand only. On the right the same shape is the ending `ou`, and
struck alone it types Midi4Text's placeholder glyph for it, `*`.

## What is settled

Settled and validated: the four Series and their composition rules (reproduce 98.26% of the
shipped dictionary, `midi4text-analysis/validate.py`); the chord assignment for all four
Series; the word-boundary rule; capitals; the Dosh escape and toggle.

Not settled, and deliberately out of scope for v1:

1. **Briefs.** None. The syllabic rules alone give 1.83 strokes/word.
2. **Command arguments.** "Cap previous N words" needs its digit shapes chosen.
3. **The residue.** 1.74% of the shipped dictionary is not reproduced by the rules, mostly
   generator inconsistencies. **v1 implements the rules, not the dictionary** — there is
   nothing to be bug-compatible with.

## Architecture: steno's shape, none of its machinery

The decisive facts are that a stroke translates on its own and nothing later revises it,
and that undo is a count of characters. Together these remove almost everything the steno
path exists to provide.

| stage | steno | Orsy |
|---|---|---|
| chord accumulation | whole board, first release commits | **same** |
| stroke type | `Stroke`, 23 steno keys | 18-bit mask, own order |
| translation | NFA over a binary dictionary | **pure function over ~110 table rows** |
| multi-stroke matching | longest match, retranslates | **none** |
| output | `Typer` with replace/undo protocol | **ring buffer, backspace N** |

So Orsy borrows steno's *front* (accumulate the whole board, fire on the first release — not
Taipo's per-side rollover, which is wrong here because both hands form one chord) and
replaces everything behind it. It needs neither `bbq_steno::dict` nor `bbq_steno::typer`.

## Crate layout

    bbq-orsy/                    no_std, no dependencies, host-testable
      src/chord.rs               two u16 hands, the four Series masks
      src/tables.rs              transcribed from orsy-mapping.json
      src/compose.rs             chord -> output, the composition rules
      src/output.rs              spacing, capitals, undo
      src/write.rs               word -> fewest strokes, for the host (`std` only)

    bbq-keyboard/src/layout/orsy.rs
      accumulation and the mode handler; converts scancodes to chord bits

A separate crate for the same reason `bbq-steno` is one: it is pure logic that wants host
tests, and the host tools can then exercise it. It does **not** depend on `bbq-steno`.

## Core algorithm

    fn translate(chord: Chord) -> Option<Translation>

1. Split the 18 bits into four Series by mask.
2. Look up each in its table (onset, second, vowel, coda); a combination a table has no
   entry for makes the stroke untranslatable.
3. Choose the nucleus: the free combinations (`ea` and `ou` with a second character, a
   placeholder glyph without); the diphthongs (`au`, `ai`); the Series 3 vowel; or, with no
   Series 3, the mirrored-vowel rule (Series 2 supplies the nucleus, append silent `e`,
   close the word).
4. Spell the onset (the onset clusters, and `XI` as `h` after `p`, `w` and `r`), then the
   coda, with the bare final `y`.
5. Emit `text` plus two flags, `space_before` and `space_after`, and the rules the stroke
   used, for the trainer.

`midi4text-analysis/m4t/theory.py` is the reference; it is ~150 lines and the port is
close to mechanical.

## Output stage

Much smaller than the steno typer, because nothing is ever retranslated.

    struct Output {
        recent: [char; 64],      // the characters typed, for retro-cap
        strokes: [Stroke; 8],    // per recent stroke: characters typed, and the
                                 // spacing and capital state it started from
        pending_space: bool,
        pending_cap: bool,
        all_caps: bool,
    }

- **Spacing.** A space is emitted before a word unless the previous stroke suppressed it.
  The word-boundary rule maps directly: ending-form vowel → space after; plain vowel → no
  space after; empty Series 3 → no space before.
- **Capitals.** `pending_cap` is set by cap-next and by the sentence-ending marks, and
  consumed by the next letter. All caps holds until the word closes, through the
  apostrophe and the hyphen. Uncap clears both.
- **Join.** Clears the space owed to the next word.
- **Retro-cap.** Walk back N word boundaries in `recent`, backspace, retype, putting the
  first capital on or taking it off. The commands use N = 1.
- **Undo.** Backspace `strokes[last]` characters and pop, and put back the spacing and
  capitals as they were before that stroke. That is the whole of it.
- **Escaped backspaces.** A backspace played through the Dosh one-shot erases a character
  the stage did not type away, so it is taken off the record and off the last stroke's
  count.

## Mode integration

`LayoutMode::Orsy` is behind the `orsy` feature, which `jolt-embassy-rp` builds by default,
and is dispatched in `LayoutManager::handle_event` beside `Taipo` and `Steno`. It is in the
mode cycle after taipo, but the boards it is for have no mode key, so it is reached from
Dosh by the toggle chord or a lone tap of an Fn key.

The Dosh escape needs the layout manager, not the crate, so `OrsyManager` returns it as an
`Escape`:

- **One-shot** — left inner `i`+`Sp`+`Bk` held with any right-hand chord: the right hand's
  9 bits are injected into the taipo engine on the Dosh table for that stroke only, so they
  get its modifier handling. A backspace played this way is reported to the output stage,
  and `.` `!` `?` set its pending capital.
- **Toggle** — all four inner keys of the left hand: a mode switch to taipo on the Dosh
  table. `0x388` is unmapped in Dosh, so its entry there is the one that switches back.
  There is no `MinorMode` for it; the mode change is what the key log sees.

## Testing

1. **Differential against the Python model.** Enumerate all valid chords, compare the Rust
   output against `theory.py` through the mesa3 mapping. This is the real test and it is
   exhaustive — the whole chord space is only 262,144.
2. **Corpus.** Re-run `writer.py`'s stroke counts against the Rust implementation; strokes
   per word must come out at 1.83, and keys per word at 7.69. The check divides with
   `writer.py` over the Rust translations, so these figures do not measure `bbq_orsy::Writer`
   and are unaffected by what it chooses. Where the two differ: `writer.py` takes the
   cheapest stroke for each chunk, which opens a syllable with the Series 2 `l` or `m` where
   those are cheaper than the outer shape, and `Writer` follows the manual's rule that the
   initial character is written in Series 1. That costs it about 2% in keys per word, and
   nothing in strokes.
3. **Output stage.** Unit tests for spacing across stroke boundaries, capitals, retro-cap
   and undo.

## Not in v1

Briefs; punctuation beyond the eight spacing marks and the Dosh escape; numbers beyond the
Dosh escape; the three rare coda-only shapes; a trainer mode in the firmware (the trainer
is TaipoTeacher, on the host; see `04-training.md`); a mirrored (right-hand-marker) form of
the Dosh one-shot.

## What only hands can settle

The mapping is optimised against a corpus and validated against a model, and has been
typed since 10 September 2026. The two things measurement cannot settle are whether Orsy's
larger chords (2.25 keys per hand-cycle against Dosh's 1.66) form as fast as small ones,
and how much practice syllable division needs. Neither has an answer yet.
